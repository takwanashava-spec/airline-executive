# Airline Executive Development Roadmap

## Product direction

Airline Executive is a worldwide airline management simulation built around the decisions of an airline founder and chief executive. The game should combine an accessible executive interface with credible airline economics, operational constraints, long-term career progression and meaningful consequences.

The current prototype is the playable foundation, not the final simulation model. It already supports founder registration, worldwide hub discovery, an opening strategy, a first leased aircraft, a starter route, weekly progression, basic finances and local saving.

## Development method

Every milestone follows the same controlled cycle:

1. Define the player decision, required data and calculation rules.
2. Separate real-world reference data from game-generated values.
3. Implement one complete playable slice on a dedicated branch.
4. Check lint, production build, save compatibility and the affected player flow.
5. Review the result before merging it into `main`.
6. Tag unresolved realism questions for the data-audit track instead of guessing.

New features should not be added directly to the large `components/airline-game.tsx` file. Shared types, simulation rules, persistence and screens should be separated before the game expands.

## Design principles

- **Executive decisions first:** every system must give the player a meaningful choice, consequence or trade-off.
- **Realism with clarity:** calculations should be credible without turning the interface into a spreadsheet.
- **Reference versus simulation:** published airport and aircraft facts must be distinguishable from demand, slot and traffic estimates generated by the game.
- **Explainable outcomes:** the player should be able to understand why a route made a profit or loss.
- **Stable careers:** changes to the game must preserve or deliberately migrate existing saves.
- **Worldwide foundation:** `airport-data-js` remains the discovery catalogue, with verified corrections layered over it.
- **Incremental releases:** each milestone must leave the game playable.

## Immediate milestone: 0.2 Architecture and Save Safety

### Why this comes first

The current prototype keeps most state, registration, views and simulation behaviour inside `components/airline-game.tsx`. Adding multi-route, multi-aircraft and staff systems to that file would make every change harder to review and more likely to break an existing career.

### Target structure

```text
components/
  airline-game.tsx
  founder/
    founder-setup.tsx
  game/
    game-shell.tsx
    opening-menu.tsx
    command-centre.tsx
    network-view.tsx
    fleet-view.tsx
    finance-view.tsx
lib/
  airport-system.ts
  game-data.ts
  game/
    create-career.ts
    simulation.ts
    persistence.ts
    migrations.ts
types/
  game.ts
```

The exact split may be adjusted during implementation, but responsibilities must remain clear:

- `types/game.ts`: shared game-state and domain types.
- `create-career.ts`: creates a valid starting airline from founder choices.
- `simulation.ts`: advances time and calculates results without rendering UI.
- `persistence.ts`: loads, validates and saves careers.
- `migrations.ts`: upgrades older saved careers when fields are added.
- Screen components: display state and send player decisions to the game layer.

### Save model requirements

- Add a numeric `saveVersion`.
- Give each career a stable `careerId`.
- Record `createdAt` and `updatedAt`.
- Validate local-storage data before treating it as a career.
- Recover safely from invalid or incomplete saves.
- Migrate the current v1 career, including careers created before CEO fields existed.
- Keep simulation calculations out of persistence code.

### Definition of done

Milestone 0.2 is complete when:

- the registration and dashboard still look and behave as they do now;
- the main game file is reduced to orchestration rather than containing every screen and formula;
- a new career can be created, saved, refreshed and continued;
- a pre-CEO save can be loaded with safe fallback values;
- advancing a week still produces the expected result;
- lint and the GitHub Pages production build pass; and
- no generated build files are committed.

## First playable vertical slice after the refactor

Milestones 0.3 to 0.5 should first deliver one coherent operating loop:

1. Research a destination from the selected hub.
2. Review distance, demand, charges and aircraft suitability.
3. Open the route and choose fare and weekly frequency.
4. Assign an available aircraft.
5. Advance one week.
6. Review passengers, revenue, costs, punctuality and profit.
7. Adjust the route or fleet based on the result.

This loop takes priority over decorative dashboards or systems that do not yet affect player decisions.

## Airport and aircraft data-audit track

The audit runs alongside feature development and does not block the worldwide prototype.

### Source hierarchy

1. National civil aviation authority or official aeronautical publication.
2. Official airport operator or airport website.
3. Official manufacturer documentation for aircraft data.
4. Government statistics or published annual reports.
5. Reputable secondary sources only where primary information is unavailable.

### Audit order

1. Featured hubs and their starter destinations.
2. Airports most frequently selected during testing.
3. Major international hubs.
4. Regional and smaller scheduled airports.
5. Remaining catalogue entries as the game expands.

### Audit record

Each verified override should record:

- field corrected;
- verified value;
- source title and URL;
- date checked;
- whether the value is factual, estimated or generated by the simulation.

The interface must never describe generated runway, terminal or traffic values as verified reference data.

## Backlog rules

A proposed feature enters active development only when it has:

- a clear player decision;
- defined inputs and outputs;
- a place in the simulation model;
- an acceptance test; and
- no unresolved dependency on an unfinished earlier milestone.

Ideas that do not meet these requirements remain in the backlog rather than being added ad hoc.
